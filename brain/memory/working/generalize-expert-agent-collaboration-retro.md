# 专家协作通用化复盘

## 背景

专家房曾将生图、办公等专家特征直接写进平台运行时和界面，导致状态重复、初始化误操作、成果类型丢失、修订入口分裂，以及工具失败被包装成伪成果物。新增专家时必须持续修改 KnowMe，违背通用 Agent 平台的定位。

## 本次形成的约定

- 专家通过版本化能力清单声明工具、连接器、交付物、完成条件和输出路由；平台只解释契约，不识别专家身份。
- 工具证据与交付物分离。需要真实文件的任务必须产生可验证的 artifact reference，普通答复留在对话中。
- 任务状态只有一个主展示位置；输入、确认、补充和返修共用同一个 composer。
- 成果物预览是按类型分派的通用组件；图片缩略图和大图均保持完整比例，状态与操作不覆盖媒体。
- 恢复历史坏数据属于启动迁移，不能进入正常执行路径。
- 未知但格式安全的成果类型必须原样持久化，避免每增加一种 Agent 交付类型就修改平台。

## 验证策略

- 对全部内置专家逐一运行声明交付物的执行、验收、返修和完成状态机。
- 对缺失 AI 配置、缺失工具、错误成果类型、成果数量不足、工具成功但证据不完整等异常路径建立测试。
- 使用真实渲染器与本地图片验证专家房只有一个输入框，图片可见、按比例完整预览且无控制台错误。
- 平台核心代码不得出现具体专家 ID；特殊能力只能来自声明式契约或隔离的历史迁移。

## 后续守则

新增或优化专家时，优先修改专家包的 `EXPERT.md`、能力清单、技能和工具绑定。只有当出现跨专家、可复用的新协议能力时，才修改 KnowMe 平台，并同步扩展契约矩阵和异常测试。
