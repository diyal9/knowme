# KnowMe v0.5.0 版本计划：从可用平台到可信工作伙伴

状态：Draft

起点：v0.4.0 结构与平台基线
版本主题：**产品属性、使用体验、Agent 专业度**

## 北极星

用户打开自己的本地文件夹或 GitLab 项目后，能够清楚知道“KnowMe 了解什么、现在要做什么、为什么这样做、成果是否可信”，并通过我的 KnowMe、专业 Agent 或显式工作流完成一条可恢复、可验收的工作闭环。

v0.5.0 不以新增页面、专家数量或底层框架为成功标准。成功标准是：核心任务更容易开始、更少中断、更可靠完成，且每个对外标记为“生产可用”的 Agent 都有与当前配置绑定的真实任务证据。

## 版本原则

1. **一个稳定心智。** 我的 KnowMe 负责长期工作关系和路由；专业 Agent 负责有边界、可验收的委托；工作流负责显式多步骤协作；管线服务负责外部长期运行。
2. **简单任务保持简单。** 解释、改写和一步任务不被迫经历复杂规划；只有关键未知项、权限变化或不可逆操作才打断用户。
3. **状态由宿主决定。** 计划、阻塞、审批、执行、验证和完成由版本化任务状态驱动，模型文字不能直接宣告权限或成功。
4. **证据先于承诺。** 能力包可加载、路线可执行和专业结果合格是三层不同结论，界面与发布说明必须明确区分。
5. **收敛优先。** 复用现有 Context Engine、任务投影、执行凭据、恢复策略和 qualification 体系，不再建设第二套并行运行时。

## Epic A：强化 KnowMe 产品属性

### 目标

让用户在首次使用、进入项目和选择工作方式时形成一致心智，不需要理解内部的 Agent、Skill、Connector、Run 等实现名词。

### 交付

- 统一首次启动、绑定目录/GitLab、进入项目、开始第一项工作的引导链。
- 明确“我的 KnowMe / 专家协作 / 工作流 / 管线服务”的适用场景、入口和返回路径。
- 在项目、会话、任务、成果和 Brain 之间显示同一工作上下文与来源边界。
- 用成果、历史和下一步行动表达价值；能力、权限、模型和连接器细节进入按需展开的诊断层。
- 统一空状态、受限状态和未配置状态，所有状态都提供可执行下一步。

### 验收

- 新用户不查文档即可完成“绑定项目 → 发起任务 → 获得并打开成果”的受控测试。
- 四类工作方式的名称、入口说明和任务归属在首页、侧栏、任务房与设置中不互相矛盾。
- 用户能回答当前内容来源、任务作用范围以及成果保存位置。

## Epic B：打磨端到端使用体验

### 目标

让核心任务从输入到交付连续、可预测、可恢复，减少重复确认、重复状态和失败后的死路。

### 交付

- 一个主要行动区统一呈现澄清、计划确认、操作审批、能力授权、重试、验收与继续讨论。
- 输入框和附件草稿在等待、失败、切换与重开后保持正确；审批期间仍可追问、改要求和取消。
- 审批成功后自动从检查点继续；重启后不重复写入、发送或调用外部副作用。
- 统一错误归因与恢复文案，明确区分缺材料、缺权限、缺环境、工具失败、结果未知和验证失败。
- 统一成果预览、版本切换、修改意见、再次交付和完成摘要；补齐键盘操作、可访问名称和焦点管理。
- 建立核心链路的启动、首响应、工具等待和完成耗时基线，再以 P95 改善作为性能目标。

### 验收

- 核心任务不存在空白等待、矛盾主按钮、丢失输入、重复消息或点击后无反馈。
- 批准/拒绝、执行中取消、断线重连、进程重启、修改要求和成果重开均有确定性回归用例。
- 发布前完成伙伴对话、专家委托、工作流、知识检索四条桌面端纵向走查。

## Epic C：提升 Agent 专业度

### 目标

把“专业”从 persona 和长提示词升级为任务范围、方法、工具、交付合同、验证器和真实样例共同约束的可证明能力。

### 交付

- 收敛生产专家名册；未通过认证的专家明确显示“待专业验收”或受限能力，不进入生产承诺。
- 为每个生产专家定义任务边界、必要输入、判断方法、交付格式、证据要求、失败边界和领域验收器。
- 资格与 Agent 版本、Skill/Connector 版本、模型配置和运行时指纹绑定，关键变化后自动失效并重验。
- 对需要外部能力的每条条件路线保存真实执行证据；失败或结果未知不能被文本总结伪装为完成。
- 建立跨专家评测矩阵：正常任务至少 2 个样例，并覆盖 edge、retry、revision、reopen。
- 将首轮成功率、自动恢复率、用户干预次数、延迟、成本和错误完成率按专家与场景报告。

### 验收

- 生产名册中的每个 Agent 均通过当前配置指纹下的完整 qualification gate。
- 零越权、零已知重复副作用、零无证据完成；领域成果通过对应验证器。
- 简单任务不会因专业流程而过度规划，复杂任务不会在关键输入缺失时开工。

## 版本推进顺序

### R0：收敛与基线

- 补齐或明确结转 4 个缺工件 change；将活跃 OpenSpec 从 19 个降到不高于 12 个。
- 把已完成 change 归档，把重复或同一用户旅程的 change 合并到同一版本主题。
- 记录核心任务成功率、干预次数、P50/P95 延迟和当前 qualification 状态。

### R1：产品心智与首程

- 收敛 `establish-my-knowme-personal-agent`、`establish-project-work-context`、`unify-personal-agent-workbench-handoffs`。
- 完成首次使用、项目进入、任务路由和成果去向的统一体验。

### R2：核心任务体验

- 收敛 `fix-agent-display-contracts`、`generalize-expert-agent-collaboration`、`harden-expert-plan-confirmation`、`unify-single-expert-commission-lifecycle`。
- 以真实桌面任务验证等待、审批、恢复、修订和重开。

### R3：专业资格与证据

- 以现有 `production-qualify-all-experts` 为唯一资格主 change，不再创建重复认证体系。
- 完成 7 个生产专家及其条件路线的当前配置 qualification report；未通过者从生产名册降级或标记受限。
- 解决必需 Skill 的上下文预算、路线证据和领域验证缺口。

### R4：发布候选

- 冻结范围，只修阻塞缺陷。
- 完成安装/升级、干净用户数据、旧任务迁移、核心桌面 E2E 与发行包 smoke。
- 输出制作人验收、测试报告、已知限制和发布说明。

## 版本指标

| 维度 | 指标 |
|---|---|
| 产品心智 | 首次任务完成率；四类工作方式误选率；项目/任务/成果归属理解率 |
| 体验 | 核心任务成功率；无效确认次数；用户干预次数；恢复成功率；P50/P95 完成耗时 |
| 专业度 | 各 Agent qualification 覆盖率；首轮合格率；修订后合格率；错误完成率；证据完整率 |
| 可靠性 | 重启恢复率；重复副作用数；状态矛盾数；不可恢复死路数 |

R0 先记录真实基线；后续目标必须相对基线设定，禁止用测试总数代替产品结果。

## 非目标

- 不为追求完整度新增一批专家、连接器或页面。
- 不重写现有 Agent 运行时，也不并行建设第二套上下文、审批或恢复系统。
- 不在本版承诺云端知识同步、跨设备协同或大规模企业管理能力。
- 不把内部枚举、原始工具名、token 或调试信息提升为默认用户界面。

## 发布门禁

1. `npm run check` 全绿，架构硬顶无新增。
2. 目标 change 的 qa-plan、code-review、acceptance、test-report 和 evidence 完整。
3. `npm run audit:production-capabilities` 返回 production/execution/qualification 三项通过，或发布说明明确移除未通过的专家/路线承诺。
4. `eval:experts:matrix` 与真实模型 qualification report 覆盖全部生产名册。
5. 干净用户数据下完成核心桌面 E2E、旧数据升级验证和发行包 smoke。
6. GitNexus 变更影响与循环依赖检查无新增高风险；所有直接依赖均已覆盖测试。
