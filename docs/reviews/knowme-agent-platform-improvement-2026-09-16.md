# KnowMe 与专家体系：平台能力和对话体验整改方案

日期：2026-09-16。状态：P1 兼容适配层已实施，P2-P4 按下述顺序继续推进。

## 本轮已落地

- 审批等待不再隐藏任务对话框；审批卡只负责批准/拒绝，输入框固定进入无工具讨论通道，可追问、改要求或取消，文字不会触发授权。
- 新增 `workbench-task-action` 任务行动投影，统一澄清、计划确认、操作审批、能力授权、重试、验收和讨论的主动作及允许命令。
- 审批成功且宿主返回可恢复检查点时，任务房自动调用“基于执行结果继续”；运行时仍以执行回执和幂等检查阻止已批准操作重放，恢复失败才保留手动恢复入口。
- 规划入口增加宿主复杂度分流：普通解释允许一阶段计划且不强制能力名，工具/多交付物/依赖任务仍要求完整能力和至少两步；未决问题仍阻止计划回执。
- 导入工作流验证现在会重新检查每个专家的技能/连接器运行依赖；静态引用存在但必需依赖被禁用时，验证失败并阻止该专家继续启动。
- 新建或保存的自建专家会持久化“待专业验收”资格标记；能力中心明确显示该状态，允许受控试用，但不把结构校验误报为专业能力已验证。
- 为审批与讨论分离、未澄清时禁止计划确认补充确定性测试；完整渲染器和后端回归均通过。

这一步是 P1 的兼容适配层，后续运行时状态迁移和审批自动续跑继续复用该投影，不要求一次性重写旧任务。

## 范围与证据边界

覆盖伙伴对话、专家协作、自建/导入专家及工作流中的 Agent 节点。统一基础协议，保留不同业务入口和会话隔离；工作流的显式人工节点不应被自动跳过。

本轮读取了规划、运行前检查、执行恢复、审批回写、专家包校验、专家提示词治理、任务房间和评测入口。GitNexus 查询因 FTS 不可用未提供调用链，旧索引不能证明覆盖完整；以下结论以源码为依据，不声称完成所有专家的实际运行验收。

## 已确认的共同问题

| 证据 | 当前行为 | 整改方向 |
|---|---|---|
| `src/shared/expert-planning-contract.ts`、`src/domain/expert-collab-plan.ts` | 从中文标题、字段、问号及编号解析规划状态 | 模型输出结构化计划提案，宿主验证后持久化；自然语言仅作展示 |
| `src/lib/expert-task-runtime.ts` 的 `preparePlanConfirmation` | 要求完整计划且至少两步 | 按复杂度选择直接答复、轻量执行、多步任务，允许一步任务 |
| `src/renderer/features/expert/ExpertTaskRoom.tsx`、`ExpertTaskAccess.tsx` | 房间和审批卡分别决定提示、按钮及输入状态；待审批时隐藏整个输入框 | 一个宿主任务投影提供当前行动，始终保留追问/改需求/取消的对话能力 |
| `src/lib/tool-execution-approval-checkpoint.ts`、`ExpertTaskAccess.tsx` | 批准后记录结果并提供再次继续按钮 | 成功回写后后台自动续跑；重启后可恢复，UI 不承担调度 |
| `src/lib/expert-task-tool-preflight.ts` | 已共用部分注册和治理逻辑，但运行前仍构建元数据工具面 | 运行前与执行时解析同一能力目录和可用性原因，执行时再次检查权限 |
| `src/lib/agent-recovery.ts` | 已有错误分类、重试和参数修复策略，部分错误仍依赖文字归类 | 工具适配器产出统一错误与副作用状态；文本兼容仅留在边界 |
| `src/lib/expert-prompt-governance.ts`、`agent-package-validate.ts` | 已有提示词、格式、权限和完整性校验 | 增加执行就绪与场景质量资格；导入成功不等于专业能力已验证 |
| `package.json` 的 `check` | 后端测试、lint、渲染测试与类型检查；真实专家评测和 E2E 为独立入口 | 发布必须关联真实模型与桌面任务证据，测试条数不能替代体验验收 |

现有 Context Engine、工具注册表、恢复策略、执行凭据和专家评测脚本是可复用基础，不建议另造第二套并行运行时。也不能据这些发现断言所有专家均失败；需要跨类型验收确认影响。

## 职责边界

KnowMe 负责会话、任务状态、能力解析、权限、工具调度、取消、恢复、审批、交付证据和界面行动。专家包负责专业范围、判断方法、输入输出要求、可选技能和领域验收器。模型负责提出计划、专业推理、生成内容和修正策略，不能以自然语言直接宣告权限或任务完成。

模型适配器单独验证结构化输出、工具调用、长内容、流式中断和上下文容量。能力不足时应限定该模型可承担的任务并说明原因，不能仅靠更长提示词弥补。

## 目标协议

扩展现有 WorkbenchTask，增加版本化、由宿主维护的任务投影，而非让前端拼接多个状态：

- `phase`：理解、规划、执行、验证、完成、失败、取消。
- `blockers`：可能有多个阻塞条件，区分信息、权限、操作审批、环境、外部结果待核对。
- `nextAction`：当前最重要且实际可执行的行动及其对象 ID、版本和选项。一个行动可以有批准/拒绝两个互斥选择。
- `allowedCommands`：当前允许的讨论、修改要求、补充材料、取消及明确审批命令。
- `planRevision`、`attemptId`、`checkpoint`：避免旧计划、重复点击和迟到回调影响新任务。
- `operationReceipts`、`artifacts`、`verification`：实际执行和交付证据。

后端依据事件更新投影并验证每次状态转换。前端、右侧状态、通知和重开会话均读同一投影。模型生成的文字不能触发状态转换。多个阻塞原因按依赖呈现，处理一个后继续展示剩余条件，不能简单丢掉其他问题。

## 规划和执行

1. 问答/改写等简单请求直接处理；需要工具的一步任务可用简短说明开始；多步骤且有依赖的任务才展示计划。
2. 计划声明目标、步骤依赖、验收、必要输入、可采用的默认值、所需能力。只有会实质改变结果的未知项才向用户提问；问题可成组回答，避免逐条盘问。
3. 只为范围变化、确有需要的用户决策或权限边界请求确认。既有授权覆盖的低风险行为不重复确认；计划确认不能自动扩大操作授权。
4. 执行前检查实际工具、工作目录、依赖和输出路径。能力问题归因到内置工具、环境、权限或连接器；禁止一律引导能力中心。
5. 每步记录输入版本、结果和验证，失败从相关步骤恢复。需求修改后仅重做受影响步骤；需重新审批的目标或内容必须使旧审批失效。

## 审批与异常恢复

对任务授权范围内、可回退的本地工作区修改，可设计任务级授权与变更预览，减少逐文件中断。已有权限边界由宿主执行；删除重要内容、范围外写入、对外发送等根据具体操作要求确认。迁移不得暗中扩大现有授权。

审批绑定操作目标、完整内容摘要、任务/运行 ID 和版本。用户预览到的内容必须与实际执行一致。批准后由后台调度恢复；拒绝后遵循拒绝含义，提供调整方案，不能立即重复相同申请。

执行器先持久化操作意图，再执行，再记录结果。崩溃恢复依据幂等键、目标核对和执行记录决定能否继续；外部操作不能假定天然具有“恰好一次”语义。

| 情况 | 平台处理 | 用户所见 |
|---|---|---|
| 参数不合法且尚未执行 | 按 schema 修正，限制次数 | 必要时显示简短修正进度 |
| 只读请求临时超时 | 有界退避重试或切换来源 | 正在重试及可取消入口 |
| 写操作结果不明 | 查执行凭据和目标状态，禁止盲重放 | 明确需要核对的结果 |
| 缺少权限或环境 | 命名具体条件，提供直达入口 | 可操作的授权/配置指引 |
| 模型回复中断 | 保存步骤与有效产物，从检查点恢复 | 已保留什么、正在恢复什么 |
| 成果验证失败 | 在预算内修正并复验 | 仅在需要用户决策时打断 |
| 无法恢复 | 保存进展与准确错误 | 原因、已产生修改、推荐下一步 |

## 对话体验

- 对话始终允许追问、改要求和取消。审批时发送“为什么要写这个文件”应得到解释，不能被当作授权，也不应启动第二次执行。
- 一个主要行动区，与同一任务投影绑定；状态文字简短且不重复播报。诊断、原始工具名和 token 信息移至详情。
- 澄清问题可直接回答；审批卡说明目的、目标、变更预览和结果；批准后自动继续，避免再点一次“继续”。
- 修改执行要求时明确是排队、暂停后调整，还是使旧审批失效；保留用户输入草稿和附件。
- 进度更新既有进度项，重要结果进入历史。轮询/流式事件重发不能制造重复消息。
- 断线、刷新、重启后还原同一行动；审批卡加载失败要有重试读取入口，不能显示空白等待或伪造补充信息请求。

## 成果与专家准入

完成条件按任务目标检查。网站任务检查文件、构建/启动、页面与基本交互；数据分析检查数据来源、计算和表格；文档检查完整内容与可打开性；生图检查真实图片及需求匹配；外部操作检查目标端结果。

占位内容不能作为完整网站交付，但不能用全局关键词过滤所有文件：空文件或 TODO 在合法开发过程中可能合理。应结合文件角色、当前步骤与交付合同识别不完整成果，并由专业验收器阻止虚假完成。

专家新建、导入、升级共用校验链：结构和依赖 → 当前环境可执行性 → 隔离任务样例 → 专业结果验证 → 就绪状态。资格绑定专家版本、运行时、技能/工具版本和模型配置，关键变化后重新验证。用户可以保存草稿或试用未验证专家，但界面不应将其标成已验证可用。

## 实施顺序与完成条件

| 阶段 | 交付 | 完成条件 |
|---|---|---|
| P0：证据和基线 | 隔离 QA 环境、复现任务、运行链路记录、已知缺陷清单 | 能稳定复现澄清误判、空工具、占位产物、审批与恢复问题 |
| P1：统一状态与对话行动 | 任务投影、宿主转换校验、对话命令路由、单一行动区 | 同一任务各入口一致；可追问；按钮可执行；重复点击无重复操作 |
| P2：统一执行与恢复 | 能力解析、工具结果协议、审批自动续跑、检查点恢复 | 内置能力归因准确；批准后继续；重启不重复写入或发送 |
| P3：规划与交付质量 | 结构化计划、按复杂度分流、领域验收器、模型能力矩阵 | 简单任务不被迫规划；未决关键输入不能执行；无实际成果不能完成 |
| P4：体系准入与发布 | 新建/导入/升级共用认证、旧任务迁移、发布门禁 | 新旧专家遵循相同机制；旧会话可继续；发布证据可追溯 |

按垂直任务链逐步切换到新协议；旧入口经过兼容适配器，避免所有入口一次性重写。迁移可回滚，保留原始历史及操作凭据。界面调整与运行时版本一起验证，再同步用户运行时。

## 跨专家验收矩阵

至少覆盖 Web、文档、数据分析、生图、外部连接器操作、自建专家、导入专家，以及伙伴对话和工作流 Agent 节点。每类运行成功任务、缺少材料、能力不可用、执行失败、修改要求和重新打开等适用场景。

共用必测：多轮澄清；简单一步任务；默认值；批准/拒绝；等待期间追问；连点提交；执行中取消；进程重启；审批内容变更；授权撤销；外部操作超时但已成功；部分成果保留；成果修订；旧任务迁移。

确定性门禁要求：零越权、零误报完成、零已知重复副作用、零相互矛盾主行动。真实模型成功率按任务类型和模型分别报告，并记录样本数、首轮成功率、自动恢复率、用户干预次数、延迟和成本；不能仅报告平均分或测试条数。发布要求所有承诺支持的路径具有真实端到端证据；暂不可验证的路径明确标记受限。

复用 `eval:experts:live`、`eval:experts:matrix`、`test:e2e` 和现有 qualification 指纹体系。开发单测、可控集成、真实模型、Electron 交互和实际成果检查分别承担不同证据，互不替代。
