# 风险导向测试设计

## 从规则推导状态机

先列需求来源、适用对象/时间/单位、状态、动作、允许转换、必须成立的不变量、明确豁免和未定规则。每个预期都要能回指这些规则；不把未规定的状态码、自动合并、过期键行为、存储实现或成功时限补成硬预期。

将风险写成“在某初态执行某动作后，哪个不变量可能被破坏”，再选择最小但有区分力的用例。边界测试写清阈值下方、等值、上方及受控时钟移动；只有处于边界两侧的操作才能证明边界语义，不能在界内直接声称已越界。

## 为每条用例建立可靠判据

每条包含：需求/风险；前置身份、数据和完整初态；编号操作；权威观察点；由规则推导的预期；执行状态；证据引用。

- 保持旧态时，要记录旧内容/旧身份/旧版本并在操作后逐项对账。“内容不是 x”不能替代“与操作前权威旧值一致”，因为旧值本来可能也是 x。
- 完整性同时核对身份集合、重复/遗漏和关键字段；行数一致不足以证明不丢数据。
- 行为不变量优先于协议细节。需求只说“不得下载新结果”时验证没有新字节或可用结果，不擅定必须返回 4xx。
- 静态结构（索引、DDL、代码）只能佐证机制；动态唯一性还需权威任务计数、任务身份和副作用回执，单条冲突日志不能替代完整结论。

## 并发与崩溃窗口

并发用例从同一基线和状态机推导：先让两个参与者读取同一基线并携带同一 expected 值，再在进入不可分割的原子校验与写入之前同步释放；原子比较与更新本身不得被测试钩子拆开。明确每个控制点、释放顺序以及最终权威内容与版本。使用环境已有的同步屏障、可控延迟或假时钟；任意 sleep 或“同时点击”不能证明关键区间重叠，也不能要求两个请求在原子区内都观察到旧版本。

当规则要求请求基线等于当前版本才能提交时，一次成功提交已推进当前版本；另一个仍携带旧基线的请求不得再成功。不要为了覆盖更多结果而允许同一旧基线连续推进两次版本。若测试另一分支，应显式改变基线或前置，而不是在同一用例中静默改变条件。

崩溃恢复至少区分三个窗口：持久化前、持久化后但确认前、确认后。确认前若规范允许，结果集合只能是“完整旧态”或“完整新态”，要显式绑定内容与版本配对并排除混合；确认后必须保持已确认的新态。控制点不可用时列执行前置缺口，不编造已具备的测试设施。

取消/完成竞态同样写出两个事件及交错：取消先被权威确认、完成先被确认、二者重叠。每个分支只断言需求规定的不变量；未规定胜者或响应码时，不替产品决定。

遇到语义未定义的动作，先把观察拆成“契约已命名的状态”和“实现才可能存在的状态”。不得为了让用例看似完整而发明取消标记、记录保留/删除、版本回退/单调、补偿方式、事务、数据库、缓存、锁策略或隐藏存储。此类竞态只验证在已定义动作范围内仍可推出的不变量；其余结果在允许/禁止栏直接写“规则不足，当前不可判定”，不得再枚举假设性的数值终态，并把补齐规则作为执行前置。

## 执行与证据两轴

执行状态分为未执行、阻塞、本人实际执行、他方记录。已有日志只支持其中直接观察到的请求、任务 ID、状态和时间点；一次超时后完成与“后台可能继续”相容，但不能证明一般架构独立。设计出的新用例仍标未执行。

分别写“材料支持什么”和“还不能证明什么”。缺可核验结果或分母时不报通过率，不用用例数量代替覆盖率。已证实缺陷给实际/预期、证据、影响和最小复现；风险假设、规则空白、环境阻塞分列。

## 交付与发布

合并交付高风险用例、证据结论、待确认项、剩余风险和发布建议；优先用一张状态/用例表，不重复铺陈同一前提。用户要求“精简”时，默认控制在约 1200 个汉字内：先用一行定义共享初态和权威观察，再让每个用例只保留“场景、操作/控制点、允许、禁止”四格；覆盖清单要求什么就写什么，不另加普通路径、实现分析或技术选型。所有用例共享的“设计完成、未执行”只声明一次。表后最多三条规则缺口，不再分别展开规则、风险、逐用例子表和发布长文。用户给出长度上限时，以约 70%–80% 为目标留出格式余量，并在发送前复核全文。逐项复核所有额外预期是否由需求推出；正确主表不能掩盖附加错误。关键用例未验证、阻塞缺陷未关闭或风险未获明确接受时，不给整体通过；证据充分时允许范围限定的通过。发布建议不是发布授权，宿主交付状态也不是专业验收证据。
