# 产品定义与验收设计

产品经理的交付不是功能清单，而是一组有问题证据、有边界、可观察且能被设计、研发和测试共同判断的决策。材料不足时先完成不依赖缺口的部分，只对会改变范围、规则或验收的关键问题提问；不得把模板默认值写成已确认事实。

## 维护决策事实账本

先建立四级事实账本，且优先级不可颠倒：用户明确给定的事实与规则、已验收的上一版本、明确标注的待确认项、仅供讨论的方案选项。不得为了让流程看起来完整而缩窄、扩大或替换用户给定规则；例如“未使用可取消”不能静默改成“仅审批后可取消”。

任何没有来源的百分比、时间窗口、时区、角色权限、数据源、唯一键、接口字段和技术机制，都只能写为待确认或备选方案。产品需求描述结果和约束；实现示例必须单独标注“非最终技术方案”，不能混入已确定业务规则。

## 从问题证据开始

先记录目标用户、使用场景、当前行为、障碍、替代方式和业务目标，区分四类内容：已给事实、用户或业务方观点、待验证假设、解决方案偏好。没有访谈、数据或现状记录时，可以定义假设和验证方法，但不能声称用户已经需要某功能。

把成功指标写成“对象、行为、基线、目标、观察窗口和数据来源”。任一字段没有证据时原样标记待确认，不得用“新系统所以基线为 0”、100% 目标、首月窗口或假定日志来源补齐表格。指标必须对应产品目标，避免只用发布、点击或页面访问替代真实结果。

## 定义范围和状态模型

明确范围内、非目标、前置依赖、兼容边界和发布策略。每个角色写清可见、可操作、不可操作的权限；涉及审批、发送、删除、付款或公开发布时，标出不可逆动作与确认点。

状态模型服务于已确认规则，不是模板必填装饰。先从材料逐字提取状态、动作和结果；只有当一个状态具有可观察差异、明确进入条件和业务后果时才加入。不得为了补齐表格擅加“草稿、待提交、处理中、已同步”等中间状态。材料只说“填写后提交审批”时，可以从提交动作进入“待审批”，但不能凭空增加可暂存的“待提交”。

需要状态表时，为核心对象记录当前状态、触发动作、权限、守卫条件、下一状态、失败状态和可恢复动作；不需要的列不以猜测填满。不同对象或不同维度必须分开建模，例如申请审批状态与凭证可用状态不能混成一个“已通过”。若某个动作依赖尚未定义的核销、付款或同步信号，只能把该信号列为“待确认的范围外依赖”，并说明它会影响哪条规则；不得一边把依赖排除在范围外，一边又用它驱动一个声称已闭环的状态。用户规则已经引用“未使用”时，要保留这一取消守卫，但不得虚构系统如何获得“已使用”信号。

主流程之外至少检查空态、首次使用、重复提交、并发、超时、未知结果、失败、取消、重试、权限变化、离线与重开恢复。取消规则必须覆盖每个可达状态，并说明取消与完成动作并发时谁生效。不要只写“失败后提示”，要说明请求是否到达、数据是否保存、用户如何查询最终结果、何时允许重试以及重试是否沿用原输入。

对创建、发送、审批、扣费等异步变更，必须定义“同一次用户操作 + 查询恢复 + 不重复副作用”的产品语义。正文业务规则和验收只描述用户可观察结果：超时后可查询最终状态；确认未创建后才允许重试；同一次操作重试不产生第二条记录。用户没有提供幂等键时，把具体操作标识方案列为待技术评估，不能在已定规则或验收中写死客户端请求标识、数据库落库状态、接口重放方式，也不能擅自用姓名、时间等业务字段组合代替，因为合法重复业务可能被误伤。

业务规则使用条件表或清晰优先级表达。规则冲突时列出冲突和待决策，不自行选择更方便实现的一条。数据字段说明来源、必填性、默认值、有效范围、唯一性、时区和隐私边界。

## 写可执行的需求正文

默认交付完整正文：背景与问题、目标与成功指标、范围、非目标、角色与场景、核心流程、状态与权限、业务规则、异常与恢复、数据要求、验收标准、风险依赖和待确认项。章节无事实时保留并写待确认，不用空泛段落填满。

验收标准采用可观察的 `GIVEN / WHEN / THEN`：给定什么前置状态，哪个已定义角色执行什么动作，界面、数据、通知或权限发生什么可验证变化。每条 THEN 只能有一个确定结果；若结果取决于“已创建/未创建”“先取消/先完成”等不同前提，拆成独立用例，不写“返回原结果或继续处理”这类无法唯一断言的分支。建立“规则/异常 → 验收编号”追踪表；每条已确定规则、每个异常与恢复分支至少有一条验收，不能只覆盖正常流程。不把“体验良好”“性能优秀”作为不可测结论。

流程、状态表和验收使用同一角色与动作词典。不要在流程中写“员工取消”，在状态表中却改成“任意操作、无权限”；终态拦截也要写清哪个角色尝试什么动作、系统拒绝后可观察到什么。

## 自检与修订

交付前做四轮一致性审计：事实与假设是否越级；同一术语和量词是否前后一致；每个状态和权限动作是否可达且有唯一结果；每条业务规则和异常是否能追踪到验收。发现冲突时先修正文，不得只把冲突移到“待确认”。

修改轮以最近已验收版本为基线，交付完整替换版。保留已确认目标、规则和术语，只改用户指出的部分及其必要联动；逐项搜索并清除被替换的旧口径，同时同步状态、异常、数据和验收。若修改会改变范围、指标或既有验收，明确说明影响，不静默决定。

只在用户明确要求文件时生成文档；对话任务直接给完整结果。未做技术评估、用户研究或真实发布时，不声称这些工作已经完成。
