# Agent 包显示规范

适用于内置专家、新建专家及导入的第三方专家。执行标识和用户名称是不同字段；新增包不应依赖页面中的临时字符串替换。

## 任务模式

在 `capability.manifest.json` 的 `metadata.knowme.execution.routes` 中填写稳定、唯一、非空的 `id` 和简短可读的 `label`；`description` 用于说明用途。内置中文界面使用中文 label；第三方作者的可读名称会保留。

```json
{
  "id": "contract-review",
  "label": "合同条款审查",
  "description": "核对合同条款、风险和待确认事项。",
  "requiredSkills": ["contract-review-method"]
}
```

- 不把技能 ID 或模式 ID 当作用户标题。技能依赖的 ID 与模式 label 不必相同。
- 新建专家必须填写名称；技能/连接器通过标准绑定字段保存。
- 导入旧包缺少 label 时，统一归一化会使用可读 name、内置名称、description 或“协作方式 N”补齐，保存和重新打开保持一致。
- 空/重复模式 ID 或非数组 routes 会导致声明验证失败。不要用展示逻辑掩盖无效执行标识。
- 模式列表不静默截断。需要突出推荐项时应明确设计更多入口。
- 统一名称逻辑在 `src/shared/expert-display.ts`；前后端新增展示入口须复用它。

## 能力、权限与状态

- 列表到详情必须保留 skills/connectors；当前页的分类筛选不能阻止跨类型依赖名称解析。
- 权限必须显示允许/禁止、工具或连接器范围。空白名单表示不允许调用，缺字段表示未明确声明，二者不可混用。
- 包声明权限不代表本次任务实际获得授权。
- 授权错误、未知、缺数据都不能显示“已授权”；使用统一 `connectorAuthorizationDisplay`。
- 已确认交付约定与已验收文件成果分开投影，文本成果不要求文件引用。
- 状态和风险使用 `capabilityStatusLabel`、`capabilityRiskLabel`，未知枚举不得显示成功或低风险。

## 必须保持的回归检查

`npm run check` 包含：

- 所有真实内置专家的模式名称、数量和前后端一致性检查。
- 新建专家保存及 Hub 装配信息检查。
- 真实目录导入后的名称兼容、序列化幂等及执行字段保留检查。
- 权限允许/禁止、授权失败重试、待验收及文本交付等组件和状态检查。

新增中文内置路由若没有合适名称，会被目录契约测试拦住；应在包内补 label，而不是继续往页面里追加特殊判断。


#### 实际执行与能力声明
新建或导入的软件开发 Agent 如承诺代码包、网页文件等真实交付，执行路径须声明 `requiredTools` 和文件成果验收条件（`minArtifacts` / `requiredArtifacts` / `artifact_present`），工具须通过运行时可用性与权限检查。仅装配技能提示词不代表可创建文件或运行测试。未配置这些条件时应提供代码建议，不应承诺已实现、已运行或已测试；确认此类文件计划会在创建及重试入口暂停。此检查覆盖明确的代码文件交付描述，不能替代逐个 Agent 的能力验收。
