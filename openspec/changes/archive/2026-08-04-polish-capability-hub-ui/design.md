## Context

见 `proposal.md`。能力 Hub 由独立的原生 HTML/CSS/JS 渲染页实现，通过 iframe 嵌入工作台中央抽屉；Catalog、安装与连接器操作由预加载桥接至 Electron 主进程。当前业务交互完整，改版应限制在展示结构和渲染模板内，避免影响 IPC 和用户能力数据。

## Goals / Non-Goals

**Goals:**

- 建立与 KnowMe 工作台一致的暖灰中性设计令牌、排版与控件语言。
- 让三个能力类型共享稳定布局，同时通过标题、说明和微弱图形差异表达上下文。
- 让精选、目录、详情和添加流程形成连续的信息层级。
- 使用原生 CSS 动画和现有图标系统实现轻量反馈，保证 Electron 渲染性能。

**Non-Goals:**

- 不修改 Catalog DTO、安装状态机、IPC handler 或文件系统逻辑。
- 不引入前端框架、CSS 框架、字体下载或动画依赖。
- 不为三类 Tab 建立三套独立 DOM 或样式分支。

## Decisions

### 1. 采用“页面导语 + 紧凑工作区”两段式头部

标题、当前类型说明和条目统计构成导语；搜索、Tab 与添加按钮构成主要工作区；分类与已安装筛选作为第二层控制。这样可将品牌和导航与筛选分离，避免当前所有控件挤在同一横行。

备选方案是保留单行工具条并只放大尺寸，但无法解决窗口缩窄时的拥挤与层级问题。

### 2. 精选区使用非对称主次展示，全部能力使用两列目录卡片

精选第一项占更高视觉权重，其余项保持紧凑；全部能力在常见宽度使用两列、窄窗口退化为单列。卡片依赖边框、留白和轻微底色区分层级，不使用重阴影或三列等宽商店模板。

备选方案是继续三列卡片，但当前数据量少时会产生碎片化小卡和大片空白，也不利于描述阅读。

### 3. 用单一渲染状态驱动标题、统计和骨架

在既有 `state.tab`、`state.loading` 和筛选结果基础上增加 Tab 文案映射与统计展示，不新增全局状态。加载时直接渲染结构匹配的骨架，避免用整体透明度保留旧内容造成误认。

### 4. 动效限制为 transform 与 opacity

卡片进入采用短时 CSS 级联，悬停和按压仅改变 transform、边框与背景；尊重 `prefers-reduced-motion`。不使用持续动画，不增加定时器或动画库，降低 iframe 内 GPU 和内存成本。

### 5. 保持 Electron 安全边界

Renderer 仅渲染主进程通过 preload 暴露的 DTO，并继续通过现有桥接函数发起操作；不直接访问 `%APPDATA%`、Node API 或外部网络。HTML 字符串继续通过 `esc` 转义，改版不扩大脚本执行面。

## Risks / Trade-offs

- [新增标题与精选结构占用更多垂直空间] → 压缩工具条高度，并让主目录独立滚动；在低高度窗口隐藏非关键说明。
- [真实 Catalog 条目数量可能远高于当前样例] → 目录保持纯 CSS Grid 和一次性字符串渲染，不增加逐卡监听器；继续使用事件委托。
- [更丰富的卡片模板可能放大长文本差异] → 名称单行截断，描述限制两行或三行，元信息保持固定位置。
- [旧测试依赖现有文案或 class] → 保留关键 ID、data 属性和事件入口，优先新增 class 而非更名。

## Migration Plan

1. 更新 OpenSpec delta 与 UI 任务。
2. 调整能力 Hub HTML 语义结构、CSS 令牌和 JS 模板。
3. 执行测试、lint 与三个 Tab 的桌面窗口视觉验证。
4. 若出现回归，可单独回退三个前端文件；数据与 IPC 无需迁移或回滚。
