# Proposal: office-partner-grounded-connectors

## Why

当前 KnowMe 的写作办公搭档已经具备基础润色、飞书草稿和远程 RAG 的雏形，但用户在真实办公场景里仍然会遇到两类关键断点：

- 飞书文档链接明明给了，助手却因为连接器 `enabled / agentVisible / allowlist / user 授权` 的任一门控未满足而“看不到工具”，最终只能输出阻断提示
- 内容源目前只覆盖本地文件夹与 GitLab，缺少对 GitHub 仓库和普通网页的正式接入，导致写作助手无法稳定读取外部资料并形成可追踪的上下文

这会直接削弱“润色改写”场景的可信度。用户需要的不是泛泛改写，而是基于飞书正文、外部网页、代码仓库、本地知识库和 RAG 检索结果的专业成稿与改写。

## Target Users

- 需要围绕飞书文档继续润色、改写、扩写、整理成稿的办公用户
- 需要结合产品知识库、外部资料和代码仓库形成专业文稿的知识工作者
- 希望把“查资料 -> 读正文 -> 专业润色 -> 飞书草稿确认写入”串成一条稳定链路的团队协作者

## What

- 修正飞书工具投影与提示边界，让“工具不可见”“未授权”“缺少 allowlist”“缺少正文证据”这几类状态可区分、可解释、可恢复
- 扩展内容源，新增 GitHub 仓库读取与网页内容抓取能力，并继续复用现有 active source / file tools / 路径安全边界
- 打通写作办公搭档的专业润色链路：优先利用本地知识库、远程 RAG、飞书正文、GitHub/网页资料增强上下文，再执行润色改写
- 保持飞书写入为两阶段：先本地草稿审阅，再经用户确认生成飞书文档草稿或实际写入

## Non-goals

- 不实现任意网页登录态爬虫或浏览器自动登录
- 不支持 GitHub 写回、PR 评论、Issue 操作等远端写能力
- 不把普通网页抓取扩展成通用搜索引擎
- 不绕过现有飞书草稿确认步骤直接写入正式文档

## Success

- 用户给出飞书文档链接时，系统能明确区分“未启用连接器 / 未完成 user 授权 / allowlist 未放行 / 已有工具但尚未读取正文”四种状态
- 用户可以在内容源中添加并浏览 GitHub 仓库、网页资料，并让写作助手引用这些资料
- 润色改写场景会优先利用知识库与 RAG 命中结果，输出明显更专业、更贴近上下文的版本，而不是泛化套话
- 飞书文档、网页资料、GitHub 仓库、本地知识库与 RAG 信息可以进入同一条“阅读 -> 写作 -> 审阅 -> 飞书草稿”链路
