# Proposal: release-v0.1.1

## 一句话目标

把 StickyNotes 从“本地可用的 P0 版本”推进到“可对外分发、可验证来源、可追溯回滚的首个正式 Release”。

## 目标用户

- 首批 Windows 桌面用户：需要轻量、无打扰、数据可信的便签工具，下载后能放心安装与持续使用。
- 早期反馈用户：需要明确版本号、更新入口、安装包来源与基础隐私说明，愿意参与后续体验反馈。
- 项目维护者：需要稳定的 GitHub Release 流程、可复现构建产物与验收证据，降低每次发布的人工风险。

## 为什么做

`launch-readiness-p0` 已补齐误删防护、备份恢复、API Key 加密、检查更新等上线前基础体验，但复盘仍明确缺少代码签名、GitHub Release、LICENSE/隐私政策、Mac 实机验收。若跳过正式发布闭环继续做体验增强，用户仍无法获得可信下载入口，更新检查也缺少真实 Release 目标。

本 Story 优先完成 `v0.1.1` 首版正式发布，是后续便签体验增强、反馈收集与口碑传播的前置条件。

## 做什么

1. 补齐开源/分发基础材料：`LICENSE`、隐私政策、README 下载与数据说明。
2. 配置 GitHub Release 自动化：生成 Windows 安装包/便携包，上传 Release assets，保留可追溯版本号。
3. 接入代码签名的配置边界：支持证书环境变量；无证书时产出未签名包并在 Release notes 明示。
4. 建立 `v0.1.1` 发布清单：变更摘要、下载资产、校验信息、已知限制、回滚策略。
5. 做 Windows 发布冒烟与 Mac 实机验收记录；Mac 无法通过时必须记录阻塞项，不假设通过。

## 非目标（Non-goals）

- 不新增便签编辑、分类、搜索、云同步等功能体验。
- 不实现自动更新后台静默下载；本 Story 只保证 Release 源与手动检查更新可用。
- 不购买或申请代码签名证书；仅定义配置与验收边界，证书缺失可作为显式发布风险。
- 不承诺 Mac App Store、公证 notarization 或 DMG 设计优化。
- 不改动产品运行时知识库/记忆机制，除非 README/隐私政策需要说明现状。

## 验收标准

- 仓库存在 `LICENSE` 与隐私政策，README 明确下载、安装、数据路径、备份与隐私边界。
- GitHub Release workflow 能在 tag `v0.1.1` 下生成并上传可下载资产。
- Release notes 包含版本亮点、安装说明、校验信息、已知限制与回滚方式。
- Windows 安装包/便携包可启动、设置页版本正确、检查更新能识别 Release 状态。
- Mac 实机验收有明确证据：通过则归档截图/记录；失败则记录机型、系统版本、错误与后续 Story。

## 产品价值

首版正式发布解决的是用户信任与分发问题：下载来源可信、版本可追踪、隐私边界明确、安装失败可定位。它不直接增加功能数量，但能让后续功能增强真正进入用户手里并形成反馈闭环。
