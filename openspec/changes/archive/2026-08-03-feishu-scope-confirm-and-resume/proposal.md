# Proposal: feishu-scope-confirm-and-resume

## Why

用户连续三次反馈飞书授权链路"点了没用、重复操作"，实测复现出三个互相独立的缺陷：

1. **"补充扩展权限"永远补不完。** `FEISHU_PERMISSION_PROFILE` 的判定前缀与 `FEISHU_AUTH_SCOPES` 的申请列表长期漂移：
   - `base` 类目要求 scope 以 `base:` 开头，但飞书多维表格真实 scope 是 `bitable:app*`，永远不可能匹配；
   - `drive:` / `calendar:` 两类被判定表要求，却从未出现在申请列表里，只能碰运气靠 `--recommend` 兜。
   结果 `permissions.complete` 恒为 `false`，主按钮永久停在"补充扩展权限"。
2. **授权完成判定判错。** `checkFeishuAuthStatus` 的成功条件是"user 已登录 且 文档/知识库就绪"。而"补充扩展权限"场景下这两条在点击前就已满足，于是第一次轮询（2.5s）立刻判成功、弹「飞书授权成功」、面板自动收起——用户其实还没在飞书里点确认。
3. **对话内的权限选项是模型编的，点了不干活。** `executeDocKbSuggest` 即使每个分区都因权限失败也返回 `ok: true`，grounding 层因此认定"工具已成功"不产出授权 CTA。模型只能自行输出 suggestion 选项卡，而这些选项走 `send` / `fill`，只是把文本当成新用户消息，既不拉授权也不续跑被中断的任务。真正具备"授权后自动续跑"能力的 `knowme://feishu/auth` 链路完全没被触发。

此外，即便判定修好，"点一下就直接拉起浏览器"也缺少知情同意：用户在授权前看不到本次会申请哪些权限。

## Target Users

- 已连接飞书、但部分扩展能力（多维表格 / 日程 / 妙记等）未开通的办公用户
- 在对话中触发飞书能力、被权限中断的用户

## What Changes

- **权限画像与申请列表对齐**：`base` 判定改为 `bitable:app`，并把 `drive` / `bitable` / `calendar` 的只读 scope 显式写入申请列表；新增一致性校验函数与单测，锁死"判定要求的能力必须真的被申请过"这条不变量。
- **授权前二次确认**：点击"一键授权 / 补充扩展权限"先展示确认面板，按能力名列出本次将申请的权限、可展开查看原始 scope，用户确认后才拉起浏览器。
- **授权完成判定按缺口收敛**：发起授权前对缺失能力集合做快照，完成判定改为"缺口集合缩小或 complete 转真"；等待超时且缺口无变化时，明确告知哪些能力未获批（通常需管理员审批），并把主按钮降级为次要重试，不再假成功、不再诱导无限重复点击。
- **对话内权限中断走确定性 CTA**：`executeDocKbSuggest` 聚合各分区的 `missing_scopes`；当所有分区都无数据且存在权限缺口时返回 `code: 'missing_scope'`，让 grounding 输出既有的「补齐授权并继续」按钮——该按钮已具备增量授权 + 自动续跑原提问的能力。

## Non-goals

- 不迁移到飞书官方 authorization code flow（继续复用 lark-cli device flow）
- 不改动飞书写入的两阶段草稿确认流程
- 不为模型自由生成的 suggestion 选项新增授权动作类型（改为让确定性 CTA 优先接管）

## Success

- 完成一次授权后，设置页卡片状态真实反映权限变化；未获批的能力被点名，不再无限循环"补充扩展权限"
- 授权前用户能看到本次申请的能力清单并可取消
- 未真正完成授权时不会出现"飞书授权成功"提示
- 对话中因飞书权限中断时出现「补齐授权并继续」按钮，授权后自动续跑原提问
