## Why

能力 Hub 已能展示和管理专家，但“试聊专家”只在后端构造一个临时对象，用户点击后不会进入 KnowMe 对话，导致专家能力停留在目录展示层。需要把“发现专家 → 安装/启用 → 独立对话 → 持续复用”打成可感知、可恢复的产品闭环，让能力目录真正转化为用户工作入口。

## What Changes

- 将专家详情主操作改为状态驱动入口：未安装为“安装并开始”，已停用为“启用并开始”，已安装启用为“开始对话”。
- 点击主操作后关闭 Hub，在工作区创建并激活一个绑定该专家的独立持久 Session，不污染当前对话，也不改变全局默认专家。
- 专家 Session 顶部和空状态持续展示专家身份、适用任务、能力绑定与依赖就绪情况，并自动聚焦输入框。
- 缺失或未授权的依赖不阻止进入对话；系统明确显示受限能力和“去配置”入口，实际工具调用仍遵守权限、allowlist 与审批门禁。
- 统一专家对话的 Session 创建路径，移除会产生孤立临时对象的前端调用；所有失败结果必须真实反馈。
- 既有 Session 继续使用创建时的专家快照；专家更新、停用或卸载仅影响未来 Session 及当前工具安全策略。

### 目标用户

- 希望从 KnowMe 能力目录快速找到并立即使用专业工作伙伴的普通用户。
- 安装了办公、写作、知识或研发专家，需要在多个独立对话中稳定复用其人格与能力绑定的高频用户。

### 验收标准

- 用户从专家详情到可输入的专家独立对话最多执行一次主按钮点击，且不会出现空响应或孤立 Session。
- 三种专家状态展示正确 CTA，并在安装、启用或建会话失败时停留原界面、显示可操作错误。
- 新对话清楚展示当前专家、可执行场景及未就绪依赖；依赖未就绪仍可进行不依赖该能力的普通对话。
- 重启后专家 Session、专家绑定和快照均可恢复；后续更新或卸载专家不改变已有 Session 的 persona。

### 非目标（Non-goals）

- 不在 Hub 抽屉内嵌第二套聊天界面。
- 不把所选专家设为所有新对话的全局默认专家。
- 不在当前已有对话中热切换专家或混合旧上下文。
- 不绕过连接器授权、工具 allowlist、风险确认或写操作审批。

### Modified Capabilities

- `capability-hub`: 专家详情提供状态驱动的直接使用入口，并把启动意图安全交给工作区。
- `expert-runtime`: 专家不再以孤立 ephemeral 试聊作为主入口；新专家 Session 可在依赖未就绪时降级创建并冻结可解释快照。
- `agent-session-tabs`: 从 Hub 启动专家时创建、激活并持久化独立 Session，显示专家身份且支持重启恢复。

## Impact

- Renderer：`src/capability-hub.js`、`src/workspace.js`、`src/workspace-agent.js` 及相关样式/空状态。
- Main/IPC：复用 `agent-session-new`，收敛 `expert-try-chat` 重复路径；专家快照继续由主进程创建。
- Runtime：`src/lib/expert-runtime.js` 与 `src/lib/agent-context-assembly.js` 继续提供 persona、技能和连接器绑定；增加依赖状态的可解释投影。
- Tests：补充 Hub CTA、跨 iframe 消息、专家 Session 激活、依赖降级、快照稳定和 Electron 冒烟覆盖。
- 不新增第三方依赖，不改变 `%APPDATA%\KnowMe\` 数据根目录。
