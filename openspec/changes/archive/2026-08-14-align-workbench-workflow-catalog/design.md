## Context

参见 `proposal.md` 的动机。Daemon 已在 `/api/workflows` 响应中提供 `catalog.visibility`、`category`、`order`，并在自身 WebUI 中将 `primary` 与 `advanced` 分组；KnowMe 的主进程客户端目前只保留名称、描述和标签，渲染进程因此只能自行按使用频率选三个推荐项，并把其余流程全部展开。

Electron 边界保持不变：主进程中的 Daemon 客户端负责请求与不可信响应规范化，预加载 IPC 只透传现有 overview 结构，渲染进程只消费已规范化的普通对象。目录条目规模很小，排序与过滤均在内存中完成，不增加启动 I/O、网络请求或持久化数据。

## Goals / Non-Goals

**Goals:**
- 让 Daemon 成为目录可见性与排序的单一事实源。
- 在客户端边界保留安全、兼容的目录元数据。
- 让常用与高级流程形成明确但可搜索的两级目录。
- 保持旧版 Daemon 与本地离线工作流可用。

**Non-Goals:**
- 不复制 Daemon WebUI 的视觉样式或完整表单结构。
- 不修改现有 IPC 名称、请求路径和任务启动协议。
- 不缓存或写回 Daemon 的目录定义。

## Decisions

### 1. 在主进程客户端规范化 catalog

`normalizeWorkflow` 将输出固定形状的 `catalog`。缺失元数据按 Daemon 的兼容规则补为 `primary/general/1000`；仅接受 `primary` 和 `advanced`，隐藏或非法可见性在 overview 边界过滤。

选择这一方案是因为主进程是外部 HTTP 数据进入 Electron 的信任边界。备选方案是在渲染层直接读取原始对象，但会让非法元数据进入搜索、统计和其他调用方，且无法复用测试契约。

### 2. 目录排序使用 order + 原始顺序

每个分组按 `catalog.order` 升序稳定排序，相同值保留接口顺序。这样与 Daemon WebUI 的目录意图一致，也避免名称排序改变业务优先级。

备选方案是继续按最近使用排序；该策略会让两端目录顺序不一致，因此最近使用只保留为独立运行记录，不再改写目录主顺序。

### 3. primary 直接展示，advanced 原生折叠

渲染层使用两个明确分组。`primary` 始终直接展示；`advanced` 放入默认关闭的 `<details>`，搜索命中时自动显示匹配结果，使高级能力既不占首屏又不被永久隐藏。

备选方案是保留“前三个 + 查看全部”，但它混合了常用与高级语义，无法解释为什么某些流程首屏出现，也会在 Daemon 增减流程时重新造成列表膨胀。

### 4. 可见数量与搜索共用同一目录集合

首页数量、列表、搜索和打开流程都从同一个已过滤集合读取，避免 UI 声称有更多流程却找不到条目的不一致。

### 5. 本仓库注入的试验流程在注册源标记为 deprecated

`game-dev-delivery` 由 KnowMe bootstrap 写入 Daemon，不属于 Daemon 原生目录。将其注册元数据改为 `deprecated/delivery/90`，再通过现有 bootstrap 幂等同步到 Daemon 索引。这样两端会依据同一目录契约将其移出用户选择面，同时保留工作流文件、脚本注册和历史任务，避免物理删除导致既有任务无法解释或恢复。

## Risks / Trade-offs

- [旧 Daemon 不提供 catalog，仍可能展示较多流程] → 按 `primary` 向后兼容，升级 Daemon 后自动获得分层；不采用名称白名单。
- [未来 Daemon 新增可见性枚举] → 未知值关闭式过滤，并通过测试明确；待双方协议更新后再显式支持。
- [高级流程可发现性下降] → 使用带数量的清晰折叠标题，并让搜索覆盖高级组。
- [当前 Daemon 已服务端过滤 internal/deprecated，客户端过滤看似重复] → 保留边界防御，确保旧服务或异常响应不会泄露内部流程。
- [流程仍保留在磁盘上，可能被误认为未移除] → 明确本次“去掉”指退出可选目录；保留文件只服务历史兼容，后续确认无恢复需求后再物理清理。

## Migration Plan

1. 先扩展客户端规范化与单元测试，确保旧响应兼容。
2. 再切换渲染分组与样式，保留现有卡片点击和启动逻辑。
3. 运行测试、lint 与 OpenSpec 校验后重启 Electron 验证。
4. 如需回滚，仅恢复客户端字段与渲染分组；没有数据迁移或持久化格式需要回退。
