## Context

参见 `proposal.md` 的 Why。当前 Runtime 的协议与治理能力已具备，但用户在导入前和异常态中的决策信息不完整，导致“状态可用但行为不可执行”。本设计聚焦 Electron 渲染层与协议映射层的可解释性升级，不改变既有 RunManager 作为状态权威的架构边界。

## Goals / Non-Goals

**Goals:**

- 在导入前提供可执行决策面板（能力、权限、兼容、风险、成本、回滚）。
- 在运行态提供“阻塞原因 + 下一步动作 + 预计等待”的统一反馈组件。
- 在取消与恢复流程中提供分阶段可视化反馈，减少误操作与重复点击。
- 保持主进程、渲染进程、IPC 边界清晰，避免把运行策略散落到 UI。

**Non-Goals:**

- 不改造 Runtime 核心状态机定义与持久化格式。
- 不新增外部依赖或复杂可视化框架。
- 不引入远程控制平面或新的权限审批系统。

## Decisions

1. **导入向导采用“预检快照 + 分级风险标签”**
   - 决策：主进程新增只读预检接口，返回能力、权限交集、协议兼容、预计成本等级、回滚建议；渲染层只负责展示与决策提交。
   - 原因：维持 IPC 单向数据流，避免在渲染层重复权限计算。
   - 备选：在渲染层直接读取 manifest 并计算；放弃原因是规则漂移和安全边界模糊。

2. **运行态统一为 Guided Recovery Panel**
   - 决策：新增状态驱动组件，消费 `agent-message-state` 聚合数据，输出标准动作（重试、降级、切换、补输入）。
   - 原因：减少多处条件分支导致的文案与动作不一致。
   - 备选：保留各节点自定义提示；放弃原因是维护成本高、跨场景体验不一致。

3. **取消/恢复采用显式阶段枚举**
   - 决策：`cancel_requested / cancelling_children / cancelled` 与 `resume_pending / resumed / resume_failed` 作为 UI 过渡态，仅由主进程事件驱动。
   - 原因：用户可感知系统是否仍在收敛，避免误判“卡死”。
   - 备选：仅保留最终态；放弃原因是中间过程不可见，用户焦虑高。

4. **性能与内存策略**
   - 决策：面板数据按 runId 增量更新，最多缓存最近 N 次 run 摘要，详情按需展开。
   - 原因：避免长会话下 DOM 与对象增长造成页面抖动。
   - 备选：全量常驻；放弃原因是会随 run 树规模线性膨胀。

## Risks / Trade-offs

- **[风险]** 指引动作过多导致用户选择困难  
  **→ 缓解**：按严重级别仅展示 1 个推荐动作 + 2 个备选动作。

- **[风险]** 预估成本不准确引发信任问题  
  **→ 缓解**：仅展示等级和区间，并标注“估算值”与影响因素。

- **[风险]** 新增状态映射与旧 UI 分支冲突  
  **→ 缓解**：先在 feature flag 下灰度，逐步替换旧分支。

## Migration Plan

1. 增加主进程导入预检 IPC 与渲染侧向导入口（默认隐藏在 feature flag 后）。
2. 引入 Guided Recovery Panel，并接入现有 WAITING/FAILED/CANCELLED 状态。
3. 接入取消/恢复阶段事件，逐步替换旧“单终态提示”分支。
4. 完成 Electron smoke、QA 反模式走查后默认开启。
5. 若回归，关闭 feature flag 回退到旧 UI，不影响 Runtime 核心执行。
