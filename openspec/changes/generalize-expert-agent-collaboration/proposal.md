# Why

专家协作曾把生图、办公等专家的身份和特定流程写进 KnowMe 运行时与界面，导致新增或优化专家时必须同步修改平台代码。工具成功、真实成果、对话说明和验收状态之间也缺少统一契约，出现了假完成、空图片、重复状态、输入框消失和修改链路割裂等问题。

# 目标用户

- 使用专家完成知识工作、研发、分析、内容、设计等任务的终端用户。
- 只维护 Agent 包、Skill、Connector 与 SOP，不应修改 KnowMe 平台代码的专家开发者。
- 需要按任务编号、证据、版本和异常原因定位问题的产品、研发与测试人员。

# What Changes

- 以 Capability Manifest v3 声明输入、交付物、工具、连接器、真实成果和完成条件；平台仅解释契约，不按专家 ID 分支。
- 将文本答复、文件成果与媒体成果分开呈现：普通结果留在连续对话中，只有显式文件或真实媒体才进入统一成果预览。
- 建立工具调用、Artifact 引用、任务交付物、验收和修订的闭环；未满足数量、类型或证据条件时不得进入验收。
- 专家在工具完成后仍提供专业交付说明；说明模型失败时保留已验证成果并使用中性回退文案。
- 任务房始终保留唯一输入框，状态在输入框上方就近展示；修改意见从同一输入框提交，多成果物时先明确目标。
- 将历史专家特判隔离为启动期数据迁移，不参与新任务执行。

# 验收标准

- 任意专家包声明相同工具与连接器契约时，无需修改 KnowMe 即获得相同工具面和成果处理能力。
- 所有内置专家均有显式 v3 Manifest，加载时不依赖 legacy adapter。
- 生图任务只有拿到可读取的真实图片 Artifact 后才能进入验收；单图、多图、动图、失败、重试和修订都有自动化覆盖。
- 文本型专家默认输出完整连续对话；用户明确要求导出或文件时才生成文件成果。
- 正常、缺能力、未授权、工具失败、成果类型错误、成果数量不足、应用重启恢复与多成果修订均有测试。
- 全量测试、lint、渲染层测试与类型检查通过，并完成所有内置专家的契约适配验证。

# 非目标（Non-goals）

- 不在 KnowMe 内实现每个专业领域的提示词、审美判断或业务方法论。
- 不为单一专家新增专属页面、按钮或状态机。
- 不把模型生成的文字声明当作工具执行或真实文件的证据。
- 不在本变更中替换所有第三方模型或连接器供应商。

# Impact

涉及专家 Manifest、任务运行时、Agent 工具装配、Artifact 契约、任务持久化、专家任务房及对应测试。现有历史生图任务通过独立迁移模块兼容，新任务只走通用契约。
