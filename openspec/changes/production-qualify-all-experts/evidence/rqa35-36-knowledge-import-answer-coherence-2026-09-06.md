# RQA35–36 — 知识/导入专业方法与通用回答收口

## 本轮结论

本轮继续按“实际装配是否配得上专家名称”审查，而不是以 Skill 数量判定能力。知识策展专家此前必需的 `knowledge-steward` 主要面向开发仓库 `brain/wiki` 与 OKF 操作，不能独立支撑通用知识策展；智能体运维专员虽已有预览、规划、导入和引用验证工具，但缺少“安装不等于可运行”的专业保证方法。两项均已补齐为候选包，并将 7 个普通专家的重复回答成果统一合并为一次连贯对话。

没有执行真实模型、知识库写入、外部项目扫描/导入、连接器探测、用户 APPDATA 写入或 UI 验收。本轮工程证据不构成专家生产资格，24 专家总体目标继续 ACTIVE。

## RQA35：知识策展专家

- E/C/L/catalog 从 2.0.0 单调升级至 2.1.0。
- 新增必需核心 `knowledge-curation-method` 1.0.0；原 `knowledge-steward` 降为可选的仓库/OKF 操作辅助。
- 方法覆盖典型检索任务、来源台账、稳定标识、完全/近似重复、版本与冲突、权限继承、责任人和保留期、生命周期、真实检索验证以及修订连续性。
- 未执行真实查询时只能给验证计划；未获授权不得删除、归档、改权限或把个人记忆升为组织知识。
- 两个名义输出合并为一个 `answer`，默认直接在对话中呈现。

## RQA35：智能体运维专员

- E/C/L/catalog 从 1.3.0 单调升级至 1.4.0。
- 新增必需核心 `capability-import-assurance` 1.0.0，预览与提交两个阶段都必须装配。
- 方法覆盖来源完整性、不可变预览令牌、最小依赖闭包、版本/哈希/ID 冲突、权限差异、明确确认、安装回执、部分失败、凭据保护、回滚和重试边界。
- 就绪度统一分为 `installed`、`enabled`、`ready`、`verified`。当前 `verify_imported_workflow` 若只返回引用存在，就只能报告静态引用验证，不能宣称连接器可达、工作流已实跑或生产可用。
- 两阶段均改为 `answer`：确认前给精确计划，确认后给安装回执和分级验证；不再默认生成文档成果。

## RQA36：回答成果通用收口

目录扫描发现 7 个普通专家仍把同一次回答声明为两个独立成果，容易产生重复成果卡和割裂对话。为以下专家的第二部分统一声明 `mergeInto: output-1`：

- 内容策划专家
- 创意策划
- 数据分析师
- 软件开发工程师
- 解决方案架构师
- 用户研究员
- 视觉方案设计师

合并只改变通用成果契约，不包含专家 ID 运行时分支。智能体运维专员仍保留确认前/后两个独立阶段，因为两者之间存在真实授权边界。

## 冻结评测与证据边界

`skill-evals/knowledge-import-methods-workspace/evals.json` 冻结 4 个未执行案例：重复/冲突/检索治理、来源缺失、静态安装但运行依赖缺失、确认后快照和权限变化。断言要求不伪造治理操作、不伪造检索验证、不复用陈旧确认，并严格区分四级就绪度。

这些案例尚未进行模型对照、人工专业评分或真实连接器验证。Skill Creator 规范用于定义方法与评测边界；本轮没有把静态测试当成效果评测。

## 全量门禁中发现并修复的通用兼容问题

首次全量检查暴露旧专业合同仍假设两个独立 answer，且 `mergeInto` 后唯一包默认成果会覆盖用户自定义成果的 ID、标题和类型。GitNexus 对 `hydrateDeliverableContracts` 的修改前影响分析为 HIGH：5 个直接调用、15 个三层上游，覆盖任务创建、快照刷新、成果选择与 IPC。

最终规则为：

- 用户自定义单成果保留自己的 ID、标题和类型；
- 同时继承唯一包默认成果的 requiredSkills、evidence 和完成条件；
- 图片/文件等必须有真实 artifact 的契约仍可接管旧版 `document` 占位，避免文字冒充图片成果；
- 多成果用户合同继续按用户 ID 和验收状态顺序执行。

新增红测先复现自定义 ID 被替换；修复后任务运行时、RQA15/RQA20 旧专业合同、图片成果和当前收口 123/123 通过。旧测试中的“必须拆成两个默认成果”断言更新为新的产品契约；自定义多成果、后续验收和完整 L1 装配断言均保留。
