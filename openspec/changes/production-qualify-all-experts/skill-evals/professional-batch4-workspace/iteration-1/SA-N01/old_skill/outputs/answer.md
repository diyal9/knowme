# 桌面资料检索架构决策建议（ADR 形式）

以下全部基于题面合成材料推演，未做基准、未联网、未部署；所有性能数字均标注为**待验证目标**。

---

## 一、必须先拍板的冲突清单

| # | 冲突 | 性质 | 拍板人 |
|---|------|------|--------|
| C1 | 销售"断网8小时连续搜索" vs 安全硬要求"撤销后≤5分钟失效" | **需求级冲突，二者不可同时满足** | 技术负责人 + 安全负责人 |
| C2 | 销售"网络恢复后再同步权限" | 直接违反 C1 的撤销时限承诺，**不能采纳为唯一机制** | 安全负责人否决即可 |
| C3 | 建议稿"每10分钟同步一次权限" | 同步周期 > 5分钟保证，方案本身不合规 | 本 ADR 解决 |
| C4 | 建议稿"合并成单一工作区缓存" | 撤销 W1 无法精确清除，且会误伤 W2；与"W2 不得永久不可用"矛盾 | 本 ADR 解决 |
| C5 | 建议稿"仅在发起查询时检查一次许可" | 任务在许可有效期内开始、过期后才出结果时会泄漏；预览/旧查询缓存同样需要门控 | 本 ADR 解决 |
| C6 | "换独立索引服务即可保证 P95<200ms" | 无任何设备/索引/延迟基准支撑，是未验证断言 | 技术负责人不应据此拍板 |
| C7 | 重启后"从零重新计时" | 与 A2 一致（保守判过期），但建议稿表述模糊，需明确为"重启即视为本地许可不可信，须在线重授权或拒绝该工作区新访问" | 本 ADR 解决 |

**C1 是本决策的核心。** 我的立场：不把销售的 8 小时离线需求"偷偷批准"，也不把它"偷偷砍掉"——给出一个**有条件、可降级**的折中定义供负责人选择（见第三节选项 B/C）。

## 二、硬约束的形式化（验收口径）

把安全要求翻译成可测谓词，否则无法验收：

> **撤销时效性**：对诚实客户端，设服务端在 T₀ 撤销账号对 W1 的工作区权限。从 T₀ 起，任何**新发起**的查询、打开、缓存命中请求，若其返回内容属于 W1（标题/摘要/正文任一），必须被拒绝。允许的最大滞后 = 5 分钟（含时钟漂移、消息乱序、重试等所有尾部延迟）。

关键细化（都来自 A2 的事实）：

1. **"缓存命中"也算获取** → 权限门控必须在**返回内容的最后一道关口**（结果组装/渲染前），而不是只在查询入口。这直接否定 C5。
2. **许可模型**：`(account, workspace)` 粒度、≤5min TTL、单调递增版本 → 天然支持 W1/W2 独立撤销，W1 被撤不影响 W2（否定 C4 的合并缓存）。
3. **乱序/重放防护**：客户端持久化每个 workspace 已见过的最高 `perm_version`，只接受版本号更高的许可；旧版本一律丢弃并触发在线刷新。这是纯规则，不需要基准。
4. **重启语义**：进程重启/休眠后，若单调计时器不能连续证明许可未过期 → 该工作区进入"锁定待授权"态：可以展示 UI 骨架和"需要联网解锁"提示，但不得返回任何 W1 内容，直到在线重授权成功。**不允许靠重启续期。**

## 三、备选方案比较（均在硬要求下可行）

### 方案 A：短周期拉取 + 逐次在线授权混合

- 许可 TTL 取 5 分钟，客户端在 TTL 到期前（如剩余 ≤1 分钟时）主动续期；续期失败即锁定该工作区。
- 每次查询/打开除检查本地许可外，还向服务端逐次鉴权。
- **优点**：撤销路径最短，理论上秒级生效。
- **致命缺点**：**完全断网 = 完全不可用**。连"撤销前就已合法持有的旧资料"都搜不了。这与销售需求的最低合理部分（短期离线可用）冲突最大，且在弱网下体验最差。两名工程师 4 周做得完，但产品上等于放弃离线场景。

### 方案 B：按工作区分区的许可门控缓存（推荐）

- **数据分区**：本地索引与缓存物理上按 `(account, workspace)` 分区存放，绝不合并（解决 C4）。撤销 W1 = 只需让 W1 分区失效并清除，W2 分区不受影响。
- **读路径三重门控**：
  1. 发起时检查许可有效；
  2. 结果组装时再次检查许可仍有效且 `perm_version` 未回退（解决 C5 的"执行中过期"竞态——过期则丢弃结果，宁可让用户重试）；
  3. 任何缓存命中（旧查询结果、预览缩略图）走同一门控函数，无旁路。
- **离线策略**：许可在有效期内 → 正常搜索/打开本地已授权内容。许可过期且无法续期 → 该工作区锁定，其他工作区照常。**离线可用时长 = 最后一次成功授权后的 ≤5 分钟**，不是 8 小时。
- **撤销传播**：不依赖推送（推送不可靠），依赖"TTL 上限 ≤5min + 到期即锁"这一被动机制达成保证——即使服务端联系不上客户端，许可自然过期也会封死访问。这是本方案能兑现 5 分钟承诺的结构性原因。
- **成本**：全部复用 A2 已有能力（签发许可、单调版本、可靠计时器、单写索引），无新托管服务，2 人 4 周量级。

### 方案 C：B + "离线宽限包"（对销售需求的有条件让步）

- 在 B 基础上，联网时为标记为"允许离线使用"的工作区下发一个**加密的离线授权包**，有效期由安全负责人单独审批（例如 8 小时），密钥在服务端撤销时可配合吊销列表提前失效。
- **诚实说明**：题面 A2 **没有提供**任何离线密钥/吊销机制，只有 ≤5min 的在线许可。因此方案 C 的前提是一个**尚不存在、需安全负责人另行批准的新能力**。在获得该批准之前，C 不能作为承诺给销售的方案。我把它列在这里是为了让负责人显式拍板"要不要为销售需求追加这项投入"，而不是替他们批准。

### 取舍结论

| 维度 | A 逐次在线 | **B 分区门控（推荐）** | C 宽限包 |
|------|-----------|----------------------|----------|
| 5min 撤销保证 | 满足（最强） | 满足 | 取决于未批准的吊销机制 |
| 离线可用性 | 几乎为零 | ≤5min | 名义 8h，前提未成立 |
| W1 撤销不影响 W2 | 满足 | 满足 | 满足 |
| 实现风险 | 低 | 低-中（门控旁路是主要风险） | 高（新密码学组件+审批） |
| 2人/4周 | 可行 | 可行 | 不可行（超出范围） |

**选 B，放弃的是：销售的 8 小时连续离线需求（当前版本不交付）。** 给销售的替代话术：断网后仍可继续工作约 5 分钟，之后需短暂联网刷新许可；若业务确需长离线，走 C 的立项评审，由安全负责人决定是否投入吊销机制。

## 四、组件与数据所有权

| 组件 | 所有权 | 职责 |
|------|--------|------|
| 许可签发服务（现有服务端改造） | 服务端 | 签发/刷新 `(account,workspace)` 许可，TTL≤5min，携带单调 `perm_version`；撤销时提升版本号 |
| 文档版本服务（现有） | 服务端 | 正文与版本的权威源；本地缓存只是副本 |
| 许可管理器（客户端新模块） | 客户端 | 持有各工作区当前许可+最高已见版本号（持久化）；驱动到期前续期；重启后置工作区为"待验证"态 |
| 门控网关 Gate（客户端新模块，**唯一内容出口**） | 客户端 | 所有查询结果、打开、缓存命中、预览必须经此返回；校验许可有效性+版本不回退+分区归属 |
| 分区索引（现有索引改造） | 客户端（单写） | 按 workspace 分区存储；支持整分区删除；崩溃后从本地授权来源重建（沿用现有能力） |

**接口要点（示意签名，非最终 API）：**

- `POST /licenses/refresh {account, workspace} → {grant, exp, perm_version}` — 唯一在线入口，客户端不得伪造。
- `Gate.check(workspace, perm_version_seen) → Allow | LockAndClear | NeedReauth` — 内部函数，代码评审时确认**没有任何返回内容的路径绕过它**。
- 撤销动作 = 服务端提升该 `(account,workspace)` 的 `perm_version` 并使旧 grant 失效；客户端收到更高版本后丢弃旧许可，收到更低版本视为重放丢弃。

**W1 撤销时的清理时序**：W1 分区索引与缓存整体删除 → 删除动作本身幂等、可后台执行（因为即使没删完，Gate 也已封锁读取），所以"删除慢"不影响 5 分钟保证，只影响磁盘占用回收速度。这一点是方案 B 的关键结构优势。

## 五、失败与恢复时序（逐条对照 A2 风险）

1. **断网 + 许可未过期**：正常读写本地分区。
2. **断网 + 许可过期**：该工作区锁定，显示"需联网解锁"；W2 若有有效许可不受影响。恢复网络 → 自动 refresh → 解锁。**不会**出现"恢复网络才同步权限导致窗口期超限"的问题，因为锁在先、解锁在后。
3. **乱序/重放旧许可**：版本号比较拦截，丢弃并触发刷新。
4. **查询执行中许可过期**：结果组装时二次校验失败 → 丢弃结果返回 NeedReauth，不落任何缓存。
5. **重启/休眠**：计时器连续性无法证明 → 所有工作区置"待验证"，联网则批量刷新；断网则全部锁定（宁可误锁，不可漏放）。
6. **索引损坏/崩溃**：沿用现有"从本地授权来源重建"路径；重建期间该分区同样过 Gate。
7. **服务端不可用超过 TTL**：等价于场景 2，全工作区锁定——这是方案 B 已知且被接受的代价（可用性换安全性）。

## 六、迁移与可逆发布

否定建议稿的"直接切新索引、失败就恢复旧缓存"——旧缓存是合并式的，回滚会把不合规结构带回来。改为双轨：

1. **阶段 1**：新分区索引与旧合并缓存并存，新写入进分区索引；旧缓存只读、仅供未迁移用户。
2. **阶段 2**：灰度切换 Gate 到新路径，按账号回滚开关一键退回旧路径（回滚窗口内旧缓存仍在，可逆）。
3. **阶段 3**：全量后，**强制清除所有用户的合并式旧缓存**并按分区重建——这一步是安全整改的一部分，不设长期保留，否则 C4
