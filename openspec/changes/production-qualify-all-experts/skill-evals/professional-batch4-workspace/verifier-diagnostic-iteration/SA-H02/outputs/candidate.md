# 事件接入与派生看板架构方案

## 1. 核心结论：团队提议不成立

**判定：** “加一个消息队列便能保证永不丢失、无重复且60秒内看板可见”的提议在固定配置下**逻辑错误**。

*   **永不丢失：** ✅ 成立。构件Q（三节点多数落盘）满足持久化要求。
*   **无重复：** ❌ 不成立。构件Q契约明确“不承诺端到端exactly-once”，仅支持至少一次投递。去重必须由应用层（计算器或看板存储）基于 `eventId` 实现，不能依赖队列本身。
*   **60秒内可见：** ❌ **物理不可行**。这是本方案最大的硬约束冲突。
    *   **计算瓶颈：** 突发到达率 2400 ev/s > 计算器处理能力 800 ev/s。
    *   **积压增长：** 每秒净积压 $2400 - 800 = 1600$ 条。
    *   **最大延迟：** 即使采用FIFO，最后一条进入队列的事件需等待前面积压处理完毕。在10分钟突发结束时，积压量巨大，排空时间远超60秒。详见第3节复算。

**取舍声明：** 在不增加计算器容量（固定配置）的前提下，**无法同时满足**“全量持久化”、“不丢弃/合并事件”和“已ACK事件60秒内看板可见”。必须显式列为待批准变更（扩容计算器或放宽SLA），否则任何声称满足的方案均为虚假包装。

## 2. 可行备选方案比较

鉴于60秒SLA在现有算力下对突发流量不可达，以下方案聚焦于**数据一致性、恢复机制与迁移安全性**，并标注其对SLA的实际影响。

### 方案 A：构件D（数据库）作为唯一权威入口 + Outbox模式
*   **机制：** HTTP进程直接写入构件D。利用事务原子性，在同一事务中写入 `event_log` 表和 `outbox` 表。后台线程轮询 `outbox` 投递给计算器。
*   **ACK边界：** 事务提交成功即返回ACK。若ACK丢失，源端重试，数据库唯一键 `eventId` 拦截重复插入。
*   **去重与原子性：** 强一致。`eventId` 唯一约束保证入库去重；Outbox保证业务记录与待处理标记原子生效。
*   **消费确认：** 计算器处理成功后，删除或标记 `outbox` 记录。崩溃后重启，未删除的 `outbox` 记录会被重新投递（至少一次）。
*   **恢复方式：** 数据库自身高可用。无需额外队列状态同步。
*   **适用前提：** 写入QPS在D承载范围内（题设称足够）。
*   **失败模式：** 轮询延迟可能略高于推送；若 `outbox` 堆积过大可能影响DB性能。

### 方案 B：构件Q（日志队列）作为缓冲入口 + 应用层幂等
*   **机制：** HTTP进程将事件 append 到构件Q。Q返回成功即ACK。计算器从Q消费。
*   **ACK边界：** Q多数节点落盘成功即ACK。
*   **去重与原子性：** **弱**。Q不保证exactly-once。计算器必须在更新看板前检查 `eventId` 是否已存在（如查询看板存储或维护本地布隆过滤器/状态表）。
*   **消费确认：** 计算器处理完一批后提交offset。若在提交前崩溃，该批事件会被重投。
*   **恢复方式：** 依赖Q的持久化和消费者组的offset管理。
*   **适用前提：** 需要解耦HTTP接收与计算压力，利用Q的高吞吐缓冲能力。
*   **失败模式：** 若计算器处理慢，Q积压严重；重投时需确保看板更新逻辑严格幂等，否则双计。

### 对比总结

| 维度 | 方案 A (DB+Outbox) | 方案 B (Queue+Idempotent) |
| :--- | :--- | :--- |
| **数据权威性** | DB为单一事实来源，易审计 | 队列为临时缓冲，DB/看板为最终状态 |
| **去重复杂度** | 低（DB唯一键天然去重） | 高（需在计算侧实现幂等检查） |
| **ACK可靠性** | 高（事务ACID） | 高（多数派落盘） |
| **迁移兼容性** | 好（可直接复用现有DB结构） | 一般（需引入新中间件Q） |
| **突发抗压** | 受限于DB写入连接池/锁竞争 | 优于DB，适合极高瞬时写入 |
| **60s SLA** | **均无法满足**（受限于800ev/s算力） | **均无法满足**（受限于800ev/s算力） |

## 3. 关键数值复算（单位：事件数/秒，KiB）

**假设：** 正常态 600 ev/s，突发态 2400 ev/s，持续 600秒（10分钟）。计算器恒定 800 ev/s。

### 3.1 突发期间积压分析
*   **突发开始时刻 ($T=0$)：** 假设系统初始积压为0（稳态运行）。
*   **突发结束时刻 ($T=600s$)：**
    *   总到达量：$2400 \times 600 = 1,440,000$ 事件。
    *   总处理量：$800 \times 600 = 480,000$ 事件。
    *   **峰值积压量：** $1,440,000 - 480,000 = 960,000$ 事件。
*   **正文存储占用（仅积压部分）：**
    *   $960,000 \text{ events} \times 1 \text{ KiB/event} = 960,000 \text{ KiB} \approx 937.5 \text{ MiB}$。
    *   *注：此仅为内存/磁盘中的待处理正文，不含索引、副本开销。*

### 3.2 恢复正常后的排空时间
*   **恢复时刻 ($T=600s$)：** 到达率降回 600 ev/s。
*   **净处理速率：** $800 - 600 = 200$ ev/s（用于消化积压）。
*   **排空所需时间：**
    *   $\frac{960,000 \text{ backlog}}{200 \text{ ev/s}} = 4,800 \text{ seconds} = 80 \text{ minutes}$。
*   **完全追平时刻：** $T = 600 + 4800 = 5400 \text{ seconds}$（突发结束后80分钟）。

### 3.3 延迟验证
*   **最坏情况延迟：** 在 $T=600s$ 时到达的事件，需等待前面 960,000 个积压事件处理完才能被计算。
    *   延迟 $\approx 4800 \text{ seconds} > 60 \text{ seconds}$。
*   **结论：** 在固定算力下，**所有**突发期间及之后80分钟内到达的事件，其看板可见延迟均**违反**60秒SLA。

## 4. 推荐方案与实施策略

### 4.1 决策建议
**推荐采用方案 A（构件D + Outbox）**，但必须附带**SLA豁免申请**或**扩容计划**。

*   **理由：**
    1.  **简化去重：** 利用DB唯一键解决“无重复”问题，避免在计算器内部维护复杂的状态机，降低代码出错风险。
    2.  **迁移友好：** 现状已有HTTP进程，改造为写DB比引入新队列组件Q更可控，且DB通常已具备备份/监控体系。
    3.  **一致性保障：** 事务保证ACK与持久化的原子性，符合“成功ACK后不丢失”的最强定义。

*   **关于SLA的诚实交付：**
    *   当前架构**只能保证**数据不丢、不重、最终一致。
    *   **不能保证**60秒可见。
    *   **行动项：** 立即向产品/管理层提交变更请求：要么将计算器吞吐量提升至至少 2400 ev/s（以应对突发），要么将SLA调整为“突发期间允许延迟至X小时，平时<60秒”。

### 4.2 接口与契约设计

#### 1. 接入层 (HTTP -> DB)
*   **输入：** `POST /events` { `eventId`: string, `payload`: bytes }
*   **逻辑：**
    ```sql
    BEGIN TRANSACTION;
      INSERT INTO event_ledger (event_id, payload, status, created_at) 
      VALUES (:id, :data, 'PENDING', NOW())
      ON CONFLICT (event_id) DO NOTHING; -- 幂等插入
      
      IF ROW_COUNT() > 0 THEN
        INSERT INTO outbox (event_id, type, payload) VALUES (:id, 'CALCULATE', :data);
      END IF;
    COMMIT;
    ```
*   **输出：**
    *   若 `ROW_COUNT() > 0` 或 `ON CONFLICT` 命中但之前已ACK：返回 `200 OK` (ACK)。
    *   若事务失败：返回 `500 Error`，源端重试。

#### 2. 派生计算器 (Poller -> Dashboard)
*   **逻辑：**
    1.  从 `outbox` 拉取批次（如100条）。
    2.  计算看板增量。
    3.  更新看板统计表（使用 `UPSERT` 或累加逻辑，需确保同一 `eventId` 只累加一次）。
    4.  删除 `outbox` 中对应记录。
*   **幂等保护：** 如果计算器崩溃在步骤3和4之间，重启后会重读 `outbox`。此时看板更新逻辑必须能识别 `eventId` 是否已计入（例如：看板明细表也存 `eventId`，或使用带版本号的聚合快照）。

### 4.3 迁移切换计划

**阶段 1：双写影子模式（1周）**
*   旧入口继续服务生产看板。
*   新入口（DB方案）开启，接收相同流量，但不影响生产看板，仅用于验证数据完整性和去重逻辑。
*   **观测：** 对比新旧入口收到的 `eventId` 集合差异，确保无遗漏。

**阶段 2：灰度切流（按 eventId Hash）**
*   将 1% -> 10% -> 50% 的流量路由到新入口。
*   **去重关键：** 由于旧入口和新入口共存，同一个 `eventId` 可能分别从两路进入。
    *   **策略：** 看板更新层必须全局去重。无论来自哪个入口，只要 `eventId` 在看板明细表中存在，则忽略后续更新。
    *   **注意：** 这要求看板底层存储（如Redis或DB）支持高效的 `EXISTS` 检查或唯一约束。

**阶段 3：全量切换与旧入口下线**
*   100% 流量走新入口。
*   监控积压指标。若发现积压持续增长（因算力不足），触发告警并启动降级预案（见4.4）。

### 4.4 故障与积压验证计划

**测试场景 1：ACK丢失重试**
*   **刺激：** 模拟网络抖动，客户端发送事件后未收到响应，随即用相同 `eventId` 重发。
*   **预期：** DB中仅有一条记录；`outbox` 仅有一条待处理记录；看板仅计数一次。
*   **判定：** 查询 `event_ledger` 行数 == 1。

**测试场景 2：计算器崩溃恢复**
*   **刺激：** 计算器在处理 `outbox` 批次中途强制 Kill 进程。
*   **预期：** 重启后，未删除的 `outbox` 记录被重新读取。
*   **判定：** 看板最终数值正确，无重复累加（依赖看板层的幂等更新逻辑）。

**测试场景 3：突发流量积压监控**
*   **刺激：** 注入 2400 ev/s 流量持续 10 分钟。
*   **观测：**
    1.  `outbox` 表行数增长曲线。
    2.  计算器 CPU/IO 利用率（应饱和在 800 ev/s）。
    3.  最新 ACK 事件与看板可见时间的差值（预计会线性增长至数千秒）。
*   **判定：** 验证积压公式 $Backlog(t) = (Rate_{in} - Rate_{process}) \times t$ 是否与实测吻合。

## 5. 缺口与待确认事项

1.  **看板存储的去重能力：** 材料未说明看板底层存储是否支持高效的全局 `eventId` 查重。如果不支持，方案A/B都需要额外的“已处理ID缓存”（如Redis Set），这会带来巨大的内存成本（百万级ID）。**需确认看板技术栈。**
2.  **Outbox清理策略：** 长期运行的 `outbox` 表需要归档或删除策略，否则会影响DB性能。
3.  **算力扩容审批：** 如前所述，60秒SLA在当前硬件下物理不可达。需产品方签字确认接受延迟超标，或批准购买更多计算器实例。

**最终交付物状态：** 本方案为静态架构推演，未进行实际压测。所有数值基于题设契约计算。
